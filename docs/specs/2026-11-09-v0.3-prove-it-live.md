# ZAAFVesper v0.3 design: prove it live

Status: approved by Rifqi on 9 Nov 2026 ("Approve, start all four").

## Why

Every rule passes its fixtures, but nothing has run live as root. Rifqi chose not to set up a local VM. GitHub Actions gives this public repository free, throw-away macOS, Windows and Linux runners where root-level tests are safe. v0.3 uses them as the test lab. It also moves the build off Rifqi's own account.

## Workstreams (one session and one PR each)

| WS | Session | Delivers | Workflow file(s) |
|---|---|---|---|
| A | S3 (Sigma import) | CI on every push and PR: vet, `go test -race`, `rules validate/test`, cross builds for darwin/windows/linux, static YARA build on macOS. A release pipeline on tags `v*` builds binaries for the 3 OS, the macOS `.pkg`, `SHA256SUMS` and an SBOM on GitHub, with signed build provenance (`actions/attest-build-provenance`). The README documents how to verify a download with `gh attestation verify`. | `.github/workflows/ci.yml`, `release.yml` |
| B | S4 (Windows/Linux) | Live validation on `windows-latest` and `ubuntu-latest`: install Sysmon (Windows) and Sysmon for Linux from Microsoft's official sources with pinned hashes, start ZAAFVesper, run Atomic Red Team tests for the linked techniques (local, non-destructive tests only), and record which rules fired. The results go into `docs/validation/windows.md` and `linux.md`. | `.github/workflows/live-windows-linux.yml` |
| C | S2 (network + outputs) | Live validation on `macos-latest`. Checks whether `eslogger` can run there (Full Disk Access may be blocked; if so, document it and use the fallback), socket polling against real processes, real syslog/TLS and HTTPS webhook receivers on localhost, and the ZAAFElegia pipe end to end (build `zaaf` from its repo, pinned commit). Results go into `docs/validation/macos.md`. | `.github/workflows/live-macos.yml` |
| D | S1 (active response) | Root-level tests of response actions on throw-away runners. On macOS: kill and suspend of a test process, `quarantine_file` and `requarantine` on a test file, `remove_persistence` of a test LaunchAgent, `isolate_process` with real `pfctl`. On Linux and Windows: kill with the platform identity checks. Results go into `docs/validation/response.md`. | `.github/workflows/live-response.yml` |

## Rules for every workstream

- **Triggers.**
  - Live and test workflows run only on `workflow_dispatch`, plus `push` to branches named `validate/**` so that a workstream can run them before its PR merges.
  - CI (`ci.yml`) runs on push and pull request.
  - Release runs only on `v*` tags.
- **Least privilege.**
  - Default `permissions: contents: read`.
  - Only the release job gets `contents: write`, `id-token: write` and `attestations: write`.
  - No repository secrets are used.
  - Every third-party action is pinned to a full commit SHA.
- **Safe test content.**
  - Atomic Red Team is pinned to one commit.
  - Only tests that act on the runner itself run: no network scanning, no external targets, no credential spraying.
  - Downloads (Sysmon, atomics, ZAAFElegia) are pinned by version or commit and verified by hash.
- **Honest results.**
  - Each validation document lists, per rule or action, whether it fired or acted, failed, or could not be tested (and why), with a link to the workflow run.
  - A rule that did not fire is reported, not hidden.
  - "Validated on a GitHub runner" is not "validated on your Mac": the docs say so.
- **Files.**
  - Each workstream writes only its own workflow files, `scripts/ci/<ws>/`, `docs/validation/<area>.md` and code fixes in its area.
  - README changes are proposed in the PR description; the integrator applies them at merge.
- **Gates.**
  - Existing gates: vet, `-race`, rules, cross builds.
  - The `judge` skill.
  - An independent `security-expert` review, which for workflows covers injection, permissions, pinned actions and untrusted downloads.
- **Merge order.** A, then B, C and D in the order they become ready. A's `ci.yml` becomes a required check for the others once it is on main.
